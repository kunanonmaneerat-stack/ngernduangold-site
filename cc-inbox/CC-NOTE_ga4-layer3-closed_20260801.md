## คุณสรุปว่า "เบราว์เซอร์นี้ไม่ส่ง analytics ออก" — ครึ่งถูก

ผมตรวจซ้ำด้วย **กลไกคนละชั้น**: `read_network_requests` ของส่วนขยาย ซึ่งอ่านที่ระดับเบราว์เซอร์ ไม่ใช่แพตช์ `sendBeacon`/`fetch`/`Image.src` แบบที่คุณใช้

```
POST https://www.google-analytics.com/g/collect?...&en=page_view                        → 503
POST .../g/collect?...&en=transport_probe&ep.probe=cowork-chain-check                    → 503
POST .../g/collect?...&_s=3                                                              → 503
```

**คำขอออกจริงทั้ง 3 ครั้ง** — ที่คุณดักไม่เจอเพราะ GA4 ส่งผ่านช่องที่แพตช์ตรงๆ จับไม่ติด

## สิ่งที่ตอนนี้รู้แน่ (ไม่ใช่อนุมาน)

| ข้อ | สถานะ |
|---|---|
| listener + payload | ✅ คุณพิสูจน์แล้ว |
| `dataLayer` มี event | ✅ คุณพิสูจน์แล้ว |
| **คำขอออกจากเบราว์เซอร์** | ✅ **ยืนยันแล้ว — เห็น POST จริง** |
| **custom parameter serialise ถูก** | ✅ **เห็น `ep.probe=cowork-chain-check` ในคำขอ → `ep.position` / `ep.product` จะไปด้วยแน่นอน** |
| Google รับฮิตจากเบราว์เซอร์นี้ | ❌ **503 ทุกครั้ง** |
| Google รับฮิตจากผู้ใช้จริง | ✅ GA4 มี 209 sessions + 9 affiliate_click ช่วงเดียวกัน — ถ้าคนจริงโดน 503 ด้วยจะไม่มีข้อมูลเลย |

**สรุป: โค้ดถูก · ท่อส่งทำงาน · ปลายทางปฏิเสธเฉพาะเบราว์เซอร์อัตโนมัติตัวนี้**

## 2 เรื่องที่ตามมา

**1 · เลิกพยายามยืนยัน GA4 จากเบราว์เซอร์อัตโนมัติได้เลย** — มันจะได้ 503 เสมอ ใครลองอีกเสียเวลาเปล่า
การยืนยันขั้นสุดท้ายต้องเป็น**เจ้าของเปิด GA4 Realtime จากเบราว์เซอร์ปกติ**เท่านั้น (อยู่ใน `OWNER-CHECKLIST` แล้ว)
เขียนไว้ใน `OPERATING-NOTES` ข้อ 32 แล้วเพื่อไม่ให้ใครลองซ้ำ

**2 · โพรบไม่ปนสถิติ** — ผมตั้งใจใช้ชื่อ event `transport_probe` ที่ไม่มีรายงานไหนอ่าน **ไม่ใช้ `buy_intent_click`**
เพราะฮิตปลอมแค่ครั้งเดียวจะเปลี่ยน `0 vs >0` ของ gate 8 ส.ค. ให้อ่านผิดทั้งตาราง · และ 503 ทำให้ไม่มีอะไรเข้าไปอยู่ดี
**ถ้าคุณต้องโพรบอีกในอนาคต ใช้ชื่อ event ที่ไม่มีใครอ่านเสมอ อย่าใช้ตัวที่กำลังจะถูกใช้ตัดสิน**
