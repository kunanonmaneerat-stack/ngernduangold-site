ฉบับแรกบอกว่า "วิธีที่ CC อยากใช้ (GA4 internal traffic filter) ยังทำไม่ได้ ต้องรอเจ้าของ"
**ตอนนี้ทำเสร็จแล้ว และระหว่างทางเจอต้นตอที่ใหญ่กว่าที่คิด** — อ่านสองย่อหน้านี้ก่อนลงมือ

### สิ่งที่เจอ (1 ส.ค. 2026 20:20)
ใน GA4 **มีของครบทุกชิ้นอยู่แล้ว** และดูเหมือนทำงานปกติทุกประการ:

| ชิ้นส่วน | สถานะที่เจอ |
|---|---|
| Internal traffic rule | มีอยู่ · `Internal Traffic - My IP` → `traffic_type = internal` |
| Data Filter | `Internal Traffic` · Exclude · **Active** |
| ไอพีที่ปักไว้ในกฎ | `184.22.17.215/32` |
| **ไอพีจริงของเครื่อง (วัดวันนี้)** | **`27.130.5.93`** |

ISP หมุนไอพีไปนานแล้ว → **กฎไม่ match อะไรเลย** → ไม่มีฮิตไหนได้ `traffic_type=internal`
→ ตัวกรองที่ Active อยู่ก็ไม่มีอะไรให้ตัด → **ทราฟฟิกอัตโนมัติทุกตัวถูกนับเป็นคนอ่านจริงมาตลอด**

นี่คือคำอธิบายที่แท้จริงของ `synthetic traffic 79%` — ไม่ใช่ว่าเราลืมตั้ง แต่**ตั้งไว้แล้วมันตายเงียบ**

### แก้ไปแล้วโดย Cowork (อย่าทำซ้ำ)
1. เพิ่ม `27.130.5.93/32` เข้าไปในกฎ GA4 แล้ว **เปิดกฎซ้ำยืนยันว่าบันทึกจริง** (ทั้งสอง CIDR อยู่ครบ)
2. `tools/uptime_check.py` บันทึกไอพีจริง + ชื่อเครื่องลง `.system_control/host_ip.json` ทุกวัน
3. `preflight → ga4 internal ip` (เช็กใหม่ ตัวที่ 20) เทียบกับ `policy.json → ga4.internal_traffic.ips`
   → ไม่ match = WARN · `host_ip.json` หาย/เก่าเกิน 7 วัน/อ่านเวลาไม่ออก = **WARN เสมอ ห้าม PASS**
4. เทสต์ 14 เคส รวมเคสจริงของวันนี้ · `test_preflight_checks.py` = **154 assertions ผ่านหมด**
5. `OPERATING-NOTES.md ข้อ 33` · บันทึกเหตุผลไว้ครบใน `policy.json → ga4.internal_traffic`

**⇒ วิธีที่ CC เสนอไว้แต่แรก (ให้ GA4 กันที่ต้นทาง) ใช้ได้แล้วจริง ๆ ตั้งแต่ตอนนี้**

## 🎯 งานของ CC

### 1 · แยก `ngernduangold-clicktest` ไม่ให้ยิง `affiliate_click` จริง — **สำคัญที่สุด**

**ปัญหา:** เดือนนี้มี `affiliate_click` ทั้งหมด **9 ครั้ง** และมีถึง 1 ใน 3 ที่น่าจะมาจาก clicktest เอง
ตัวเลข 9 นี้คือฐานของ gate 8 ส.ค. (`ngernduangold-buy-intent-gate`) — ถ้าฐานปน **การตัดสินใจวันนั้นผิดทั้งตาราง**

**ข้อจำกัดที่ต้องเคารพ:** ตอนนี้ไอพีของเครื่องอยู่ในกฎ internal แล้วก็จริง
แต่ **ห้ามพึ่งไอพีอย่างเดียว** — มันเพิ่งพิสูจน์ตัวเองว่าหมุนได้และตายเงียบ
ให้กันที่ **ตัว event เอง** เป็นชั้นหลัก แล้วให้ไอพีเป็นชั้นสำรอง

**ให้เลือกวิธีที่ CC ประเมินว่าปลอดภัยที่สุด แล้วบอกเหตุผล** — ข้อเสนอเรียงตามที่ Cowork ชอบ:

- **(ก) ให้ clicktest ไม่แตะปุ่มจริงเลย** — ตรวจว่าปุ่มมีอยู่/`href` ถูก/`sub_id` ถูกฟอร์แมต จาก DOM หรือจาก HTML ที่ build ออกมา
  โดยไม่ต้องคลิก · **ดีที่สุดถ้าทำได้** เพราะไม่มีฮิตให้ต้องกรองตั้งแต่แรก
- **(ข) ถ้าจำเป็นต้องคลิกจริง** ให้ยิงเป็นชื่อ event แยกที่ไม่มีรายงานไหนอ่าน (แนวเดียวกับ `transport_probe` ในข้อ 32)
  **ห้ามใช้ `affiliate_click` / `buy_intent_click`** เด็ดขาด
- **(ค) ชั้นสำรอง** — ส่ง `traffic_type=internal` ไปกับฮิตของ clicktest ตรง ๆ ด้วย ไม่ต้องรอให้ไอพี match

> **ห้ามลบข้อมูลย้อนหลังใน GA4** ตัวเลขที่ปนไปแล้วให้ปล่อยไว้แล้วอธิบายในรายงาน — การลบทำให้เทียบช่วงเวลาไม่ได้อีกเลย

### 2 · บอกกลับมาว่า gate 8 ส.ค. ควรอ่านตัวเลขไหน
หลังแยก clicktest ออกแล้ว `affiliate_click` ที่ "สะอาด" ของเดือนนี้เหลือเท่าไร
และ gate ควรนับจากวันไหนเป็นต้นไปถึงจะไม่ปน — **ระบุวันให้ชัด** Cowork จะเขียนลง `policy.json → gates`

### 3 · ถ้าเจอที่อื่นที่ยังยิง GA4 โดยไม่ตั้งใจ ให้รายงาน อย่าเพิ่งแก้
มีงานอัตโนมัติอีกหลายตัวที่เปิดหน้าเว็บ **ลิสต์มาก่อน** แล้วค่อยตกลงกันว่าตัวไหนควรกัน ตัวไหนปล่อยได้
