## 4 · direct 75% — **`uptime_check` ไม่ใช่ต้นเหตุ มันคือตัวตรวจจับ**

รายงานเขียนว่า direct = "โรบ็อตของเราเอง (uptime check ทุก 12 ชม. + งานเบราว์เซอร์)"
`tools/uptime_check.py` ใช้ **urllib ล้วน ไม่รัน JavaScript** ⇒ **สร้าง session ใน GA4 ไม่ได้แม้แต่ครั้งเดียว**

ต้นเหตุจริงถูก root-cause ไปแล้วและเขียนไว้ในไฟล์นั้นเอง (บรรทัด 69-80): กฎ internal traffic ของ GA4 ปักไว้ที่ IP **184.22.17.215**
ขณะที่เครื่องถูก ISP หมุนไปนานแล้ว → Data Filter ขึ้น Active แต่ **ไม่ match อะไรเลย** ทุก page view ที่เบราว์เซอร์ของ agent เปิดจึงถูกนับเป็นคนอ่านจริง

`uptime_check` เป็น**ที่เดียวที่รันทุกวันและมีเน็ต** จึงถูกใช้บันทึก IP ให้ preflight เทียบ — **ถ้าไปแก้มันเพราะคิดว่ามันปล่อยทราฟฟิก จะทำลายตัวตรวจจับตัวเดียวที่มี**

วันนี้ `preflight → ga4 internal ip` = **PASS** (27.130.8.134 อยู่ในลิสต์ · Filter Active) ทิศทางที่คุณให้เฝ้า 20 ส.ค. จึงถูก
**แต่ IP หมุนไปแล้ว 3 ครั้งใน 2 สัปดาห์** (184.22.17.215 → 27.130.5.93 → 27.130.8.134) ⇒ กฎที่อิง IP **จะพังอีกแน่นอน** และทุกครั้งต้องรอเจ้าของไปเพิ่ม CIDR ในหน้า GA4
ระหว่างนั้นตัวเลขเปื้อนอีกรอบ — และ gate 5 ก.ย. อ่านทับช่วงนั้นพอดี
ทางแก้ถาวรคือแบบเดียวกับที่ใช้กับ clicktest เมื่อ 1 ส.ค. (ปิดการส่งที่ต้นทาง ไม่พึ่งกฎที่เราคุมไม่ได้) — **ยังไม่ทำ รอสั่ง** เพราะต้องแตะ snippet GA4 ของทุกหน้า
